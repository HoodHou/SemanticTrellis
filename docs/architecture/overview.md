# Architecture overview

## Goal

SemanticTrellis turns repository understanding into a maintained, reviewable
asset. It separates facts extracted from source code from meaning curated by an
agent or a human reviewer.

## Layered model

```text
Repository bytes
      |
      v
Structural facts          Disposable, reproducible
      |
      v
Change set and impact     Incremental, repository-local
      |
      v
Curator proposals         Reviewable patch operations
      |
      v
Curated semantic graph    Canonical, stable, versioned
```

### Structural facts

Structural facts describe files, symbols, imports, calls, and declarations.
They are generated by parser adapters and can always be rebuilt.

The first milestone uses file hashes as the structural fact boundary. Later
milestones will introduce language-aware symbol contributions without changing
the curated graph schema.

### Change set and impact

The maintenance engine compares the current repository inventory with the last
local snapshot. It emits added, changed, and removed files and maps those files
to curated nodes through source provenance.

Future symbol-level maintenance will use the same contribution model: remove a
changed file's previous facts, insert its new facts, and re-resolve only the
definition and reference keys touched by that file.

### Curator proposals

An AI curator never writes the graph directly. It emits a patch containing
typed operations. Patch validation checks stable identity, locked nodes,
referential integrity, and source provenance before persistence.

### Curated semantic graph

The curated graph represents systems, subsystems, components, concepts,
invariants, files, and external dependencies. It is deliberately smaller and
more stable than the symbol graph.

## Application lifecycle

### Bootstrap

1. Inventory the complete repository.
2. Persist a local content snapshot.
3. Create an initial review queue.
4. In a future milestone, summarize files and ask a curator agent to propose the
   first semantic graph.
5. Review and apply the proposal as an explicit patch.

### Sync

1. Probe repository state.
2. Compute the delta against the local snapshot.
3. Find curated nodes whose provenance intersects the delta.
4. Create or update review items.
5. Update disposable structural state.
6. Leave the approved graph unchanged until a patch is reviewed.

### Audit

Audit validates graph integrity, missing source provenance, stale source paths,
and unclassified repository files. A full AI reclassification is not part of a
normal audit.

## Module boundaries

```text
CLI adapter
    |
Application use cases
    |----------------------|
Domain rules        Infrastructure adapters
    |                       |
Provider ports       File system and JSON storage
```

The domain layer is platform independent. AI providers, parser runtimes,
databases, and MCP are adapters at the boundary.

## Agent boundary

MCP is the primary machine-facing adapter. A server instance is bound to one
repository root at process start, so tool arguments cannot redirect it to a
different workspace. Read tools return structured content and human-readable
text; write tools declare their effects through MCP annotations.

Canonical graph changes use two calls. `validate_patch` applies a proposal only
in memory and returns a token derived from the current graph and exact patch.
`apply_patch` recomputes that token immediately before writing and rejects stale
or changed input. Host approval remains necessary because MCP annotations are
hints rather than an authorization mechanism.

## Planned extension points

- language parser adapters;
- AI summarizer and curator adapters;
- Git-aware file discovery;
- symbol contribution index;
- impact propagation engine;
- interactive review UI;
- MCP and coding-agent integrations;
- local database projection for large repositories.
